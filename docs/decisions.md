# Архитектурные решения

Почему система устроена именно так и где проведены границы.

## Права и роли

1. **Роль хранится в таблице `profiles`, а не в метаданных пользователя.** Метаданные (`user_metadata`)
   пользователь может изменить сам, а роль в `profiles` через API не меняет никто. Новый пользователь
   по умолчанию — исполнитель (безопасный вариант). Постановщиком делают вручную: через `app_metadata`
   при создании или `update profiles` в SQL Editor.
2. **Все сотрудники видят список профилей (ФИО, роль, должность).** Без этого исполнитель не увидит,
   кто поставил задачу и кто вернул её на доработку. Email виден тоже — внутри компании это допустимо;
   если нет, его легко убрать из выдачи.
3. **Поля задачи (название, описание, исполнитель, приоритет, срок) меняет только постановщик.**
   Исполнитель работает со статусом и обсуждением.
4. **Исполнителем можно назначить только пользователя с ролью «Исполнитель»**, не постановщика.
   Проверяется в базе.
5. **Чужая задача для исполнителя «не существует»:** на попытку её открыть или изменить он получает
   «Задача не найдена», а не «Нет прав». Так нельзя перебором узнать, какие задачи есть в системе.
6. **Сотрудник правит в профиле только имя, должность и телефон.** Роль и email меняет администратор.

## Статусы и история

7. **Статус меняется только через одну функцию базы `change_task_status`.** Прямое изменение колонки
   статуса запрещено всем на уровне прав. Правила переходов проверяет триггер на таблице задач,
   поэтому они сработают при любом изменении, даже если в будущем появится другой путь.
8. **Постановщик не двигает задачу за исполнителя** («Взять в работу», «Отправить на проверку»):
   это действия того, кто делает работу. Если понадобится «закрыть за человека», это отдельное правило.
9. **Из «Принята» переходов нет** — задача закрыта. Вернуть её можно только новой задачей.
10. **Возврат на доработку требует комментарий**, и комментарий из одних пробелов не считается.
    К другим переходам комментарий необязателен, но сохраняется, если есть.
11. **Повторный переход в тот же статус отклоняется**, чтобы не было пустых записей в истории.
12. **Смена исполнителя не пишется в историю статусов**: история — про жизненный цикл работы.
    Переназначить можно в любом статусе; статус и исполнителя нельзя менять одним запросом.
13. **Удаление задачи удаляет и её историю и обсуждение.** Через API удалить отдельные записи истории нельзя.
    Следующий шаг — архивирование вместо удаления (мягкое удаление), чтобы история сохранялась всегда.

## Объекты, деньги, обсуждение

14. **Этап объекта задаёт постановщик вручную** (подготовка, идут работы, приостановлен, сдан). Вычислять
    его из задач нельзя: «приостановлен» — решение руководителя, а не состояние задач.
15. **Готовность объекта = доля принятых задач.** Мера грубая (задачи разного объёма), но честная
    и понятная без настройки весов. Веса или процент выполнения по задаче — следующий шаг.
16. **Сводка по объекту — представление `object_summary` с `security_invoker`.** Оно считает задачи
    и расходы с правами того, кто спрашивает, поэтому отдельных правил доступа для сводки нет: исполнитель
    видит только свои задачи и нулевые суммы, постановщик — всё.
17. **Расходы видит и ведёт только постановщик.** Деньги — чувствительные данные, исполнителю для работы
    они не нужны.
18. **Объект с задачами или расходами удалить нельзя** — сначала нужно удалить или перенести их.
    Так случайное удаление стройки не сотрёт всю работу и финансы по ней.
19. **Комментарии видит и пишет тот, кто видит задачу.** Автора и время ставит база. Редактировать
    комментарии нельзя, удалить можно только свой: обсуждение — часть истории приёмки.
20. **Просрочка считается на лету:** срок прошёл, а задача не принята.

## Безопасность

21. **Регистрация закрыта в настройках Supabase.** Даже если её случайно включат, новый пользователь
    станет исполнителем без задач и ничего не увидит.
22. **Во фронте только публичный ключ Supabase.** Он сам по себе ничего не разрешает: все права
    проверяет база. Секретный ключ не используется ни во фронте, ни в скриптах репозитория.
23. **Права на таблицы выдаются только явно.** Опция «автоматически открывать новые таблицы для API»
    выключена, гранты пишутся в миграциях построчно, вплоть до отдельных колонок.
24. **Замечания Supabase Security Advisor разобраны.** Служебная функция `rls_auto_enable()` закрыта
    миграцией `004`. `change_task_status` и `is_manager` — `security definer` и доступны вошедшим
    пользователям намеренно: первая и есть API смены статуса (доступ проверяется внутри и в триггере),
    вторая нужна политикам RLS и отвечает только «текущий пользователь — постановщик?».
25. **Правила в базе покрыты автотестами** (`supabase/tests`, 93 проверки): тесты ходят в базу
    от имени разных пользователей так же, как браузер, и проверяют, что запрещённое действительно
    запрещено. Сквозной сценарий в браузере (`e2e/`) проходит приложение за все роли.
    Всё это запускается в CI на каждый пуш и пулл-реквест.

## Интерфейс

26. **Кнопки действий считаются на фронте по той же таблице переходов**, что и в базе, —
    только чтобы не показывать лишнего. Если интерфейс ошибётся или устареет (статус сменили
    в другом окне), база откажет, пользователь увидит понятное сообщение, экран обновится.
27. **Доска задач не вводит новых правил.** Перетащить карточку можно только в статус, который разрешён
    этому пользователю, а финальное слово всё равно за базой. На телефоне перетаскивания нет —
    там работают кнопки в карточке задачи.
28. **Ошибки базы показываются пользователю как есть** — они написаны по-русски
    («Переход «Новая» → «Принята» запрещён»). Системные ошибки переведены в понятный текст.
29. **Чужой объект или задача по прямой ссылке выглядят как «не найдено»**, как и в базе.
30. **Фильтры хранятся в адресе страницы**, поэтому переживают обновление, кнопку «назад»
    и их можно отправить ссылкой.
31. **Без Redux и библиотек кэширования запросов.** Каждый экран загружает свои данные сам,
    страницы подгружаются лениво. При росте числа экранов, которые делят одни данные, — React Query.

## Демо-стенд

32. **Демо-вход кнопками включается переменной `VITE_DEMO_PASSWORD`.** Без неё экран входа обычный —
    чтобы случайно не опубликовать пароль рабочей системы.
33. **Демо-данные — функция `demo.reset()` в закрытой схеме `demo`.** Ночной сброс через `pg_cron`
    вынесен в отдельный файл и не входит в миграции: рабочая база, развёрнутая из репозитория,
    никогда не потеряет данные по расписанию.
34. **Keep-alive вызывает функцию `ping()`** — единственное, что доступно без входа, и она не читает данных.
