# Решения и допущения

Что решено самостоятельно там, где ТЗ допускает разные трактовки.

## Права и роли

1. **Роль хранится в таблице `profiles`, а не в метаданных пользователя.** Метаданные (`user_metadata`)
   пользователь может изменить сам, а `profiles` через API менять нельзя никому. Новый пользователь
   по умолчанию — исполнитель (безопасный вариант). Постановщиком делают вручную: через `app_metadata`
   при создании или `update profiles` в SQL Editor.
2. **Все сотрудники видят список профилей (ФИО и роль).** Без этого исполнитель не увидит, кто поставил
   задачу и кто вернул её на доработку. Email виден тоже — внутри компании это допустимо;
   если нет, его легко убрать из выдачи.
3. **Исполнитель не может редактировать поля задачи** (название, описание), только менять статус.
   В ТЗ ему разрешены только «взять в работу» и «отправить на проверку».
4. **Исполнителем можно назначить только пользователя с ролью «Исполнитель»**, не постановщика.
   Проверяется в базе.
5. **Чужая задача для исполнителя «не существует»:** на попытку её изменить он получает
   «Задача не найдена», а не «Нет прав». Так нельзя перебором узнать, какие задачи есть в системе.

## Статусы и история

6. **Статус меняется только через одну функцию базы `change_task_status`.** Прямое изменение колонки
   статуса запрещено всем на уровне прав. Правила переходов проверяет триггер на таблице задач,
   поэтому они сработают при любом изменении, даже если в будущем появится другой путь.
7. **Постановщик не может двигать задачу за исполнителя** («Взять в работу» / «На проверку»).
   В ТЗ это действия «назначенного исполнителя». Если руководителю нужно «закрыть за человека»,
   это отдельное правило, его стоит обсудить.
8. **Из «Принята» переходов нет** — задача закрыта. Вернуть её можно только новой задачей.
9. **Комментарий из одних пробелов не считается комментарием** при возврате на доработку.
   Комментарий к другим переходам необязателен, но сохраняется, если есть.
10. **Повторный переход в тот же статус отклоняется**, чтобы не было пустых записей в истории.
11. **Смена исполнителя не пишется в историю статусов**: в ТЗ история — только про статусы.
    Переназначить можно в любом статусе; статус и исполнителя нельзя менять одним запросом.
12. **Удаление задачи удаляет и её историю.** ТЗ разрешает постановщику удалять задачи,
    а история без задачи смысла не имеет. Через API удалить отдельные записи истории нельзя.
    В реальном проекте я бы предложил вместо удаления архивировать задачу (мягкое удаление),
    чтобы история сохранялась всегда.
13. **Объект с задачами удалить нельзя** — сначала нужно удалить или перенести его задачи.
    Так случайное удаление стройки не сотрёт всю работу по ней.

## Прочее

14. **Регистрация закрыта в настройках Supabase.** Даже если её случайно включат, новый пользователь
    станет исполнителем без задач и ничего не увидит.
15. **Во фронте только публичный ключ Supabase.** Он сам по себе ничего не разрешает: все права
    проверяет база. Секретный ключ не используется ни во фронте, ни в скриптах репозитория.
16. **Правила в базе покрыты автотестами** (`supabase/tests`, 51 проверка): тесты ходят в базу
    от имени разных пользователей так же, как браузер, и проверяют, что запрещённое действительно
    запрещено. Плюс сквозной сценарий в браузере на 27 шагов (`e2e/`) на локальной копии Supabase.

## Интерфейс

17. **Кнопки действий считаются на фронте по той же таблице переходов**, что и в базе, —
    только чтобы не показывать лишнего. Если интерфейс ошибётся или устареет (статус сменили
    в другом окне), база откажет, пользователь увидит понятное сообщение, экран обновится.
18. **Ошибки базы показываются пользователю как есть** — они написаны по-русски
    («Переход «Новая» → «Принята» запрещён»). Системные ошибки переведены в понятный текст.
19. **Чужой объект или задача по прямой ссылке выглядят как «не найдено»**, как и в базе.
20. **Без Redux и сторонних библиотек для запросов.** Данных мало, каждый экран загружает своё.
    Это осознанное упрощение для объёма задания; при росте я бы взял React Query для кэша.
21. **«Мои задачи» — только у исполнителя**: у постановщика нет своих задач, он видит всё через объекты.
    Фильтр по статусу хранится в адресе страницы, поэтому переживает обновление и кнопку «назад».

## Что не успел / что сделал бы дальше

- Мягкое удаление задач и объектов вместо физического (см. п. 12).
- История изменений самих полей задачи (кто сменил исполнителя, описание).
- Пагинация и поиск по задачам — при текущем объёме не нужны.
- Обновление в реальном времени (Supabase Realtime): сейчас данные обновляются при открытии экрана
  и после своих действий.
- Сводный список всех задач для постановщика с фильтрами (сейчас — через карточки объектов).
- Запуск тестов в CI (GitHub Actions) на каждый пуш.
